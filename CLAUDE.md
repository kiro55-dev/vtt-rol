# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OpenRoll: a system-agnostic virtual tabletop (VTT) desktop app built with Tauri 2 (Rust backend) + SvelteKit / Svelte 5 (static SPA frontend). Licensed GPL-3.0-or-later. The README (in Spanish) is the product spec. Everything below "(Por implementar de aquí para abajo)" is planned, not built yet. Stage 1 (now): the game master does everything locally. Stage 2: P2P networking where each peer receives only the information the GM chooses to share.

**The code, comments, identifiers, commit messages and UI text are all in Spanish.** Keep new code in Spanish to match (e.g. `zona`, `mapa`, `entidad`, `instancia`, `tirada`, `rejilla`, `almacen`).

## Commands

Package manager is **bun** (Tauri's `beforeDevCommand`/`beforeBuildCommand` call `bun run ...`).

```sh
bun install
bun run tauri dev          # run the desktop app (Vite on fixed port 1420, strictPort)
bun run tauri build        # release bundle
bun run check              # svelte-kit sync + svelte-check (type checking)

# Frontend tests (vitest; there is no "test" script in package.json)
bunx vitest run
bunx vitest run tests/tiradas.test.ts
bunx vitest run -t "nombre del test"

# Rust tests (run from src-tauri/)
cd src-tauri && cargo test
cd src-tauri && cargo test compactar     # filter by test name
```

## Architecture

### Rust is the source of truth
All game state lives in Rust (`AppState` in [partida.rs](src-tauri/src/tablero_general/partida.rs)). The frontend never holds authoritative state. Every frontend mutation `invoke`s a Tauri command and then **re-reads** the affected data from Rust. New commands must be added to `generate_handler!` in [lib.rs](src-tauri/src/lib.rs).

### Persistence: snapshot + delta log (event sourcing)
Module split in `src-tauri/src/tablero_general/`:
- [almacen.rs](src-tauri/src/tablero_general/almacen.rs): raw disk I/O only, with no Tauri or model knowledge. Everything lives under the app data dir (`app_data_dir()`, e.g. `%APPDATA%\com.vttrol.app`), never the working directory. Each game (partida) is a folder `<app data>/partidas/<name>/` and `Almacen` works on ONE at a time (`dir()` returns a copy of the path; `cambiar_dir` switches it). Files in a game folder: `partida.json` (snapshot), `deltas.jsonl` (append-only log), `historial_personal.txt`, `imagenes/`, `archivos/entidad_<id>/`, `miniaturas/<tipo>/`.
- [partidas.rs](src-tauri/src/tablero_general/partidas.rs): the folders of the games (list, create, name validation, last opened in `<app data>/config.json`, and the one-time move of the old single-game layout into `Partida 1`, which renames items one by one with retries and keeps a `partidas/.migrando` marker until done, so an interrupted run resumes; never rename a folder that contains the others, it fails on Windows if anything has it open). No state, so `cargo test` covers it.
- [estado.rs](src-tauri/src/tablero_general/estado.rs): `EstadoPartida` + the `DeltaPartida` enum + `aplicar_delta`. It has no Tauri dependency, so `cargo test` covers it.
- [partida.rs](src-tauri/src/tablero_general/partida.rs): Tauri commands and `AppState`.
- **Renaming a game** (`renombrar_partida` → `renombrar_partida_en` in `partida.rs`, `partidas::plan_renombrado` / `partidas::renombrar`): renames the folder `partidas/<name>/` (the name IS the folder name; everything inside is relative paths, so nothing else changes). The new name goes through `validar_forma` and must not belong to ANOTHER game (case-insensitive; changing only the case of the same game is fine). Another game can be renamed with the room open; the OPEN one only with the room closed and no new ficha open: it compacts, `Almacen::soltar_archivos()` releases the open append handle (Windows cannot rename a folder with an open file; the rename also retries a few times), renames, `cambiar_dir`s to the new folder and updates `ultima_partida`; if the rename fails the `Almacen` stays where it was. On the front, renaming the open game reloads everything like switching games (its absolute data path and thumbnail cache changed). In `VentanaPartidas.svelte` the «Renombrar» button of each row turns it into a text field (Enter saves, Escape cancels); a click on the row opens the game (there is no double-click shortcut: it was tried and removed).
- **Deleting a game** (`borrar_partida` → `borrar_partida_en` in `partida.rs`, `partidas::borrar`): removes the whole folder `partidas/<name>/` (maps, fichas, images, attachments, players, history) FOR GOOD. The folder is found with `partidas::buscar` (never a path from the caller) and the state lock is held so nobody switches games meanwhile. Another game can be deleted with the room open (the room belongs to the open game). The OPEN game can be deleted too: first it switches to another one (the first of the rest alphabetically, or a new empty «Partida 1» / «Partida nueva» if it was the only one) through `cambiar_con_lock(.., guardar_antes = false)` (the one being deleted is NOT saved) and only if that worked its folder is removed; refused with the room open or a new ficha open, like switching games. The games window (`VentanaPartidas.svelte`) has a «Borrar» text button on every row (no bin icon: there is no way back); it never deletes directly: it shows a RED confirmation («¿Borrar la partida «X»? Se perderán para siempre…») whose button says «BORRAR PERMANENTEMENTE» («Cancelar» and Escape back out, but «Cancelar» disappears while deleting: it is immediate).

Invariants to preserve when adding state changes:
- **Every state change is a `DeltaPartida` variant** applied through `registrar`/`procesar_delta`. That path applies the change in RAM and appends to the log *under the same lock*, so log order equals apply order. Don't mutate `EstadoPartida` directly from a command. This is also the hook point for future networking (`// FUTURA RED`).
- Each delta line carries a monotonic `seq`, and the snapshot stores `ultimo_seq`. On load only `seq > ultimo_seq` is replayed. Broken or partial lines are skipped. The old format without `seq` is still accepted.
- Compaction (snapshot write + log truncation) runs at startup when needed, every 10 minutes, and on window close. It holds the state lock throughout. Snapshot writes are atomic (tmp + fsync + rename).
- Lock order: `estado` first, then `borradores`.
- Switching games (`cambiar_de_partida` in `partida.rs`) holds the state lock throughout: it saves the open game first (`compactar`), then switches the `Almacen` dir and loads the other one, and reverts if loading fails. It refuses while a draft entity exists (`borradores` not empty). A new game starts from `EstadoPartida::default()`, i.e. the default parameters. The front must also drop everything from the old game (`partida.#alternar`, `miniaturas.limpiar`, `tiradas.cargar`).
- New `EstadoPartida` fields need `#[serde(default)]` so old saves still load.
- Saving a ficha registers `EntidadCambiada { id, cambios }` with ONLY the fields that changed ([cambios_entidad.rs](src-tauri/src/tablero_general/cambios_entidad.rs): `entre` builds the `CambioEntidad` list, `aplicar` applies it to the bank ficha and every instance's `base`). The front still sends the whole ficha to `modificar_entidad`; Rust diffs it, and no change means no delta. `EntidadModificada` (the whole ficha) stays only to replay old logs. A new `Entidad` field needs its own `CambioEntidad` variant in `entre`/`aplicar`.

### Files and images: reference diffing, not GC
[recursos.rs](src-tauri/src/tablero_general/recursos.rs): there is no orphan sweeper. For deltas that can affect resources (`afecta_a_recursos`), the referenced image/file sets are computed before and after the delta. Anything no longer referenced is deleted only after the delta is safely logged. A crash can leave an extra file, but never a dangling reference. If you add a model field that references a file, update `referencias()` and `afecta_a_recursos()`.

- Images are content-addressed: `imagenes/<sha256 prefix>.<ext>` ([imagenes.rs](src-tauri/src/tablero_general/imagenes.rs)). The game stores **relative paths only**. The frontend converts them with `urlDeImagen()` in [src/lib/imagenes.ts](src/lib/imagenes.ts) (`convertFileSrc`; the asset protocol is limited to `$APPDATA/**`).
- Thumbnails ([miniaturas.rs](src-tauri/src/tablero_general/miniaturas.rs)): WebP generated once on demand, named after the source hash. SVG/AVIF fall back to the original. A ficha can also have its OWN thumbnail, the one the user framed in the editor: `CajaFoto` (drag = move, wheel = zoom) edits `Entidad.foto_encuadre` (`EncuadreFoto`: `zoom` 100-400 %, `x`/`y` 0-100; saved with the ficha so reopening it shows the photo as it was left; mirrored by `Encuadre` in `recorteFoto.ts`), and on save the FRONT crops the photo (`recorteFoto.ts`, a 128 px WebP via canvas) and sends the bytes to `guardar_miniatura_ficha`. Rust stores them as is in `miniaturas/ficha/entidad_<id>_<version>.webp` (a new name on each save, so no cache to invalidate) and registers the delta `MiniaturaFichaCambiada`, which sets `Entidad.miniatura_url` (bank + instances). That field is Rust-owned: `modificar_entidad` ignores the front value, keeps the saved one, and drops it if `foto_url` changed. `recursos.rs` frees the old file by reference diffing (`Referencias.miniaturas`), also when the ficha or its zone is deleted. The front uses `miniaturas.deFicha(entidad)`: the own thumbnail if there is one, else the automatic one of the photo, so bank, «Fichas activas», drag ghost and board show the same image.
- Every relative path arriving from the frontend must pass through `archivos::ruta_segura` (blocks absolute paths, `..`, and Windows reserved names).
- Entity drafts: `iniciar_borrador_entidad` reserves a real id (tracked in `AppState.borradores`) so attachments go straight into `archivos/entidad_<id>/`. Cancelling calls `cancelar_borrador_entidad`.

### Recycle bin (papelera)
[papelera.rs](src-tauri/src/tablero_general/papelera.rs): deleting a ficha (one or several at once), a map or a zone does not destroy anything.
- **What goes in.** What is removed, with its cascade (instances, the zone's maps and non-unique fichas, and copies of the unique instances that were only deactivated, `retiradas`), is stored whole as one `GrupoPapelera` in `EstadoPartida.papelera` via the delta `EnviadoAPapelera`. Instances deleted on their own and parameters do NOT go to the bin. The old `ZonaEliminada`/`MapaBorrado`/`EntidadBorrada` deltas stay only to replay old logs.
- **Ctrl+Z.** `restaurar_papelera` → `RestauradoDePapelera(id)` brings back the LAST group (reverse order). It only undoes deletions, never creations. A `retirada` gets its place back only if it is still unplaced and inactive. A unique ficha re-instanced in the meantime keeps its current instance.
- **Ids are reserved.** Nothing new takes an id that is in the bin (`papelera::reservados`, used by `crear_zona`, `crear_mapa`, `siguiente_id_entidad` and `instanciar`), so a restore never clashes and no references need rewriting. Fichas need it: their attachments folder carries the id.
- **Files.** `recursos::referencias()` also walks the bin, so nothing in it is deleted from disk. `PapeleraVaciada` frees everything by reference diffing, and `vaciar_papelera` also removes each emptied ficha's `archivos/entidad_<id>/`.
- **When it is emptied.** Only on a clean exit: closing the window (`cerrar_partida` in `lib.rs`) and when switching games (`cambiar_de_partida`). Autosave and startup never empty it, so after a power cut the bin is still there.

### Domain model
[modelos.rs](src-tauri/src/tablero_general/modelos.rs) is mirrored by hand in TypeScript interfaces at the top of [src/lib/partida.svelte.ts](src/lib/partida.svelte.ts). Keep the two in sync (serde's default enum encoding, e.g. `Cuerpo = "Pequenio" | { Grande: number[] }`). `Zona` contains `Mapa`s. An `Entidad` (= ficha) is a template in the bank. An `Instancia` is an active copy, placed on a map cell or not (`id_mapa: None`, `NoPuesto`).

Players live in [jugadores.rs](src-tauri/src/tablero_general/jugadores.rs) (registered by the room server, see «Network»; the permission helpers are ready for stage 2's player actions):
- `IdJugador = u16`; the host is `ID_HOST` (0), can do everything and is never listed. `EstadoPartida.jugadores` (`Jugador { id, nombre }`, delta `JugadorRegistrado`, ids from 1 via `jugadores::registrar`) lets a returning player keep their fichas.
- `Entidad.propietarios` lists the players who control a ficha (any type): they see it whole, edit it (except `Propietarios`/`Zona`/`Unico`, `cambio_permitido`), move, rotate and remove its instances (`controla_entidad`/`controla_instancia`). Empty = host only. `validar_entidad` only accepts registered ids, no repeats, never `ID_HOST`.
- Players may only attach `.txt` (`adjunto_permitido_a_jugador`). PDFs are banned on purpose (JavaScript, launch actions, reader exploits; no viewer dependency, the app must run on Linux).
- **Abuse caps** (anyone with the link must not be able to break the game or fill the host's disk; full list in `docs/red.md` «Seguridad»): ≤ `MAX_JUGADORES` registered, ≤ 16 connections not yet identified; names cleaned of invisible/bidi chars, unique and not reserved («rollmaster»…); no repeated ids in a request and ≤ `MAX_INSTANCIAS_PROPIAS` instances per player; ≤ 10 files / 2 MiB per ficha folder from a player (`cabe_en_carpeta`); `validar_entidad` caps name, text parameters and attachments for everyone; uploads ≤ 8192 px / 40 Mpx, own thumbnails ≤ 512 px; unused uploads are discarded when the room closes, on expel and on a new link; bounded request queue and a cut-off for players who don't read. Release builds use `panic = "abort"`: nothing reachable from a player request may panic. **A new player action needs its own caps**, not only the permission check.
- The host webview has a CSP and the `asset:` scope is limited to `$APPDATA/**` (`tauri.conf.json`); `devCsp` is null, so check a release build after changing how scripts, styles or images load.
- Dice from players: the command travels as plain text and the host's `parsear_comando` accepts only numbers, `d`, `+ - *` and `adv/desv/dis` (max `MAX_LONGITUD_COMANDO`), so typed text never reaches the breakdown. The front also renders it through `desgloseSeguro` (escapes everything but `<b>`). `Tiradas.jugador` records who rolled.

Instances:
- **Rules.** They live in [instancias.rs](src-tauri/src/tablero_general/instancias.rs): pure functions that build the delta (`InstanciaCreada`/`InstanciaModificada`/`InstanciaBorrada`/`ValorActualModificado`) with everything resolved (new id, cell fitted with `encajar`), and the commands only register it.
- **Unique fichas.** A unique ficha that already has an instance reuses it (same id and current values) instead of creating another.
- **Current values.** `ajustar_a_definiciones` keeps one current value per parameter with a maximum, The max is only the default: the current value may go above it (extra life) or below 0 (negative life), within ±`LIMITE_VALOR_ACTUAL` (16000, mirrored in `partida.svelte.ts`). A ficha is drawn grey (card and board) when any parameter with `atenuar_si_negativo` (only allowed with `tiene_maximo`; Vida has it by default) has its current value ≤ 0: `partida.estaCaida`, driven by the definition, not by any id. Old saves without the field get it only on Vida (`DefinicionGuardada` in `modelos.rs`).
- **Dragging** (banco ↔ tablero ↔ «Fichas activas») goes through [arrastreFicha.svelte.ts](src/lib/arrastreFicha.svelte.ts):
  - It uses pointer events, not HTML5 DnD (Tauri intercepts it on Windows).
  - Drop zones carry `data-destino`.
  - `accionAlSoltar` holds the whole rule table.
  - **Several fichas from the bank.** Ctrl+click selects (`partida.idsBancoSeleccionados`, ephemeral; cleared by clicking outside `.banco` or Escape). Dragging a selected row drags the whole selection (`{ entidades }` origin) → `instanciar_entidades`. On the board the first lands on the drop cell and the rest in a near-square grid (`tablero::disposicion_en_cuadricula`, mirrored by `disposicionEnCuadricula` in `tablero.ts` to draw the yellow targets). Supr with a bank selection sends it to the bin as ONE group (`borrar_entidades`); without one, Supr deletes the focused instances.
- **On the board.** Tokens are drawn by [fichasTablero.ts](src/lib/fichasTablero.ts): a square covering the body with a type-colored border (Enemigo red, NPC blue, Jugador green).
  - Left-drag on a token moves it. A ficha dropped from the bank onto the board gets NO focus (so its shapes do not show); dropped in «Fichas activas» it does.
  - **Group drag.** Dragging a focused token drags every focused token of that map (`grupo` in the `{ instancia }` origin, `instanciasArrastradas`). They all move by the same `(dx, dy)` as the grabbed one → `mover_instancias`, one `InstanciaModificada` per token (no new delta). `tablero::desplazar_grupo` (mirrored by `desplazarGrupo`) trims the common offset at the map edge so distances are kept. Dropped in «Fichas activas» they all leave the board; dropped on the bank they are all deleted.
  - **Stacking.** `Instancia.capa`: placing or moving a token on the board gives it the highest (`instancias::capa_superior`), so it draws on top; `fichasDelMapa` sorts by it and `fichaEnPunto` picks the top one. Old saves get 0.
  - Right-click without dragging rotates it 90° clockwise: `Instancia.rotacion`, and `lados_instancia`/`ladosInstancia` swap the sides around the same center.
  - Ctrl + right-click without dragging mirrors its image left-right (`Instancia.espejo`, command `espejar_instancia`, `InstanciaModificada`): looks only, so sides, cell and layer do not change; it is drawn in the token's own axis (after the rotation) and keeps turning with the rotation. Not private, so `vista_jugador` keeps it.
  - **Move with the right-drag arrow + Enter.** When the arrow was drawn from a token (`origenRecorrido` in `Tablero.svelte`), Enter moves that token the same as the arrow, so the cell you grabbed it by (the arrow's FIRST cell) ends exactly on the arrow's LAST cell and the rest of the body stays around as it was (a 3×3 grabbed by its bottom-right corner puts that corner where the arrow ends, the rest up-left): destination = its origin cell `coordenadas` shifted by (last − first), sent through `partida.moverInstancia` like a drag (Rust `encajar`s it at the map edge); then the arrow is removed. Same permissions as moving by hand: `partida.controla` on screen (host always; player only their own) and the host re-checks `mover_instancia`; if the token cannot be moved it is neither marked nor moved. While the arrow lasts, the origin token is drawn with the same dashed white outline as a focused one (`opciones.marcadaParaMover` in `dibujarFicha`, without the focus or the parameter shapes). The key guard (Enter alone, not in a field/button/link) and the destination rule are pure and tested in [moverConFlecha.ts](src/lib/moverConFlecha.ts).
  - Dragging it to «Fichas activas» takes it off the board.
- **Visibility** lives in [visibilidad.rs](src-tauri/src/tablero_general/visibilidad.rs): `vista_jugador` keeps only public parameters (and the current value of those) and drops attachments; the same function will filter what is sent over the network.
  - The host sees ALL of its parameters (private ones included) in «Fichas activas», the parameter box and the board shapes: «public» only decides what is SENT to players. `OCULTAR_PRIVADOS_AL_MASTER` (now `false`) would hide privates from the host's own screen again (`obtener_instancias_activas` would return the filtered view).
  - **Greyed-out signal.** If the parameter that greys a token (`atenuar_si_negativo`, e.g. Vida ≤ 0) is private, `vista_jugador(inst, definiciones)` still sets the derived `Instancia.atenuada = true` (never stored: always `false` in the game) so others (and the host's screen while privates are hidden) see it grey without its value; `partida.estaCaida` honours it. Owners and the host get the whole instance and compute it themselves.
- The front never filters by itself: a parameter that is missing from `instancia.base.parametros` is not shown (`veParametro`).
  - Per player: each map has a checkbox at its top-right in the map list; checked = shared with the room's players at once (`Mapa.compartido`, delta `MapaCompartido`, command `compartir_mapa`; Rust-owned like `ancho`/`alto`, so `modificar_mapa` keeps the stored value). It is independent of the map the host has open. The old `MapaPublicoCambiado` delta stays only to replay old logs. `mapas_para` gives a player the shared maps, `zonas_para` only the zones that hold one, `instancias_para` the owners' instances whole (wherever they are) and the rest `vista_jugador`, only if placed on a shared map, and `recurso_visible_para` only files used by something they see (shared map backgrounds, photos of visible instances, their own fichas); the bin, unshared maps and host-only fichas never leave. `entidades_para` sends a player only their own bank fichas. `cambios_para` filters an `EntidadCambiada` (owners get all; others only if instanced, without attachments or private parameters).
- **Full-size photo.** Double-clicking a card in «Fichas activas» opens the ORIGINAL photo (`foto_url`, not the thumbnail) in `VisorImagen` ([visorImagen.svelte.ts](src/lib/visorImagen.svelte.ts) holds only the path). It is a small bordered floating window (no backdrop) whose top-right corner sits at the pointer (clamped to the window). Pressing anywhere outside it (the press still does its normal thing), or Escape, closes it, and the `<img>` is unmounted with its `src` emptied so the webview releases it. It bypasses the `imagenDe` / `miniaturas` caches on purpose.
- **Order and focus.** `Instancia.orden` is the order in «Fichas activas», changed via `InstanciasReordenadas`. Focus is a set (`partida.idsSeleccionados`).
  - **«Este mapa» filter.** A toggle next to the «INSTANCIAS» title (`ajustesVista.soloMapaActual`, screen-only) shows only the instances PLACED on the open map (`estaEnMapa`). Everything that works on the list (`data-indice`, drag reorder, ↑/↓) uses `partida.instanciasVisibles`; a reorder of the visible ones is turned into the full order with `reordenarConOcultas` (hidden ones keep their slots) before going to Rust. The board is not filtered.
  - **Every multi-selection uses Ctrl (or Cmd)**: the bank, the board and «Fichas activas». Ctrl+click adds or removes; Ctrl+drag on the board background draws a selection box that ADDS the tokens it touches (`fichasEnRectangulo`, `partida.seleccionarInstancias`). Without Ctrl, dragging the background pans.
  - Focused tokens draw their parameter shapes, measured from the body's edges so the four reference points land on grid lines (`extremosForma`).
  - A left click anywhere outside elements marked `data-conserva-foco` clears the focus.
- **Focus is shared as a notice.** Every focus change sends `AvisoTablero::Foco` (ephemeral, not saved). A `Foco` from another player is kept in `partida.idsFocoAjeno` and drawn with a violet outline; it never changes the local focus. ↑/↓ cycle through «Fichas activas».
- **Dragging a roll** from the chat onto a value (`data-valor="idInstancia:idDefinicion"`, on the summary of a card or a row of the parameter box) subtracts its total with the left button and adds it with the right ([arrastreTirada.svelte.ts](src/lib/arrastreTirada.svelte.ts)); it goes through the same batching as the wheel.
- **Current-value edits** (wheel, −/+, dragged rolls) are batched in `partida.valoresPendientes` and sent as ONE `modificar_valor_actual` per value. They are sent 1 s after the last change, or earlier when the focus changes or the game is switched.

Entity stats (vida, armadura...) are not fixed fields. They work on three levels:
- `EstadoPartida.definiciones_parametros` (`DefinicionParametro`) holds the parameters shared by all entities. Defaults come from `parametros_por_defecto()`, with fixed ids `ID_VIDA`..`ID_RANGO_ARMA`.
- `Entidad.parametros` (`Parametro`) holds each entity's value and its `publico` flag, one per definition, in definition order.
- `Instancia.valores_actuales` (`ValorActual`) exists only for definitions with `tiene_maximo` (e.g. current vida). The entity's value is the maximum.

`Forma::Resumen` (only with `tiene_maximo`) shows `actual/max` on the instance card in «Fichas activas».

Definitions change through the deltas `ParametroCreado`/`ParametroBorrado`/`ParametrosReordenados`, which call `EstadoPartida::ajustar_a_definiciones` so every entity and instance follows (a deleted parameter disappears from all of them). The UI is `VentanaParametros.svelte`, opened from the gear button at the bottom-left of the left panel (`BotonAjustes`, which takes a list of options so more can be added in `PanelIzquierdo`).

`normalizar_parametros` keeps entities consistent with the definitions. It runs on load and in `crear_entidad`/`modificar_entidad`, and the front mirrors it in `EditorFicha`. Old saves that still have `vida_max`/`armadura`/... are migrated when deserialized, through `#[serde(from = "EntidadGuardada")]` in `modelos.rs`.

### Board (tablero)
Positions are grid cells, never pixels, like a spreadsheet: `Casilla { x, y }` with (0,0) top-left.
- **Grid.** The map is split into `max(1, round(ancho / rejilla))` columns and rows, so cells fit exactly and are almost square.
- **Map size.** `Mapa.ancho`/`alto` are owned by Rust: the real size of the background image, read from its header in `imagenes::dimensiones`.
  - `modificar_mapa` ignores the front's values.
  - `corregir_tamanos_mapas` fixes old maps with `MapaModificado` deltas when a game is opened.
  - Image formats depend on use (`imagenes::Uso`, mirrored by `UsoImagen` in `src/lib/imagenes.ts`): a map accepts no SVG/AVIF, since its size defines the cells, so every map background can be measured. A ficha's photo accepts them, since its container fixes the size. The front rejects a wrong format before calling Rust, and Rust checks again.
- **Bodies.** An instance occupies a rectangle (`Cuerpo`), and `Instancia.coordenadas` stores its CENTER cell (`tablero::extension`: on an even side, the top/left of the two central cells) so a future rotation only swaps the sides.
- **Where the logic lives.** Cell logic is in [tablero.rs](src-tauri/src/tablero_general/tablero.rs), mirrored with the same integer math in [src/lib/tablero.ts](src/lib/tablero.ts), which also does the pixel and camera side. Keep both in sync, and their tests too.
- `MapaModificado` re-fits instances of that map with `encajar`.
- **Ephemeral notices (avisos).** Pings (middle click) and the measured path (right-drag, with the start cell in yellow) are `AvisoTablero` ([tablero.rs](src-tauri/src/tablero_general/tablero.rs), mirrored in [src/lib/avisosTablero.ts](src/lib/avisosTablero.ts)), NOT deltas: never written to disk or the log, no `seq`. The board draws its own marks at once and calls `avisar_tablero`, which validates them and hands them to `Red::difundir`: pings and paths on a shared map reach the connected players (the host's focus is not shared). A notice from another player must arrive as the Tauri event `aviso-tablero`, which `Tablero.svelte` already listens to. Drawing lives in [marcasTablero.ts](src/lib/marcasTablero.ts). **Live drag:** while someone drags tokens on the board, `Tablero.svelte` sends `Arrastre { id_mapa, piezas: [{ id_instancia, casilla }] }` (only when a cell changes, ≥ 50 ms apart, plus a 3 s heartbeat) and `ArrastreFin` when it ends; the others keep them in [arrastreAjeno.svelte.ts](src/lib/arrastreAjeno.svelte.ts) and draw the token (semi-transparent) on that cell instead of its real one, which only changes when the drop's `mover_instancia(s)` arrives (a dropped one stays ≤ 1.5 s or until its real cell matches; with no heartbeat for 10 s it expires). A player's `Arrastre` may only name their own instances (`permitida`). Added in protocol version 4. **The measured path (right-drag) is throttled to one notice per 40 ms but the LAST state is always sent** (trailing send, and at once on release; `cambiarRecorrido` in `Tablero.svelte`), and a player sends it as `MensajeCliente::Aviso` (no request queue or reply, like the live drag), which the host runs through a per-connection ORDERED queue (`MAX_AVISOS_EN_COLA`): before, each notice ran in its own `spawn_blocking` and could cross, and as a `Pedir` the extra ones were dropped at 30/s, leaving a stale arrow for the others. **Each person has their own color** for arrow and ping (protocol 9): `ajustesVista.colorFlecha` (random on first use, kept in `localStorage` like the other screen preferences, changed from ⚙ → «Color de mi flecha…», `VentanaColorFlecha.svelte`: the same native color input as the grid bar «Color:», a sample arrow and a random button; pure helpers in `colorMarca.ts`). `Ping`/`Recorrido` carry `color: [u8;3]` (old notices: green) and `Recorrido`/`RecorridoBorrado` carry `jugador` (0 = host), which the HOST always overwrites when relaying (`Red::reenviar_aviso` → `AvisoTablero::con_jugador`; a client cannot pose as another). Each screen keeps ONE arrow per person (`RecorridosAjenos`), so everyone sees everyone's arrows at once.

### Network (red/)
Everything is in [src-tauri/src/red/](src-tauri/src/red/) and explained in [docs/red.md](docs/red.md) (architecture, security, how to publish, and the exact list of what stage 2 still needs). Phase 1: the host opens a room from ⚙ → «Configuración de sala» (`VentanaSala.svelte`, store [sala.svelte.ts](src/lib/sala.svelte.ts)); players open a link in the browser and use, live, the SAME app as the host with only what is shared, acting only on the fichas they own. Their actions are requests to the host (see «Player actions» below).
- **One app, two modes.** [modo.ts](src/lib/modo.ts): inside Tauri it is the host; in a plain browser, a player. All data access goes through [backend.ts](src/lib/backend.ts) (`invoke`, `listen`): **never import `@tauri-apps/api/core` or `/event` anywhere else** (only `soltarArchivos.ts` uses the webview API, and it is a no-op for players). Host: Tauri. Player: `invoke` is answered from the replica of their view ([src/lib/red/replica.ts](src/lib/red/replica.ts): read commands only; anything else is rejected), which [conexion.svelte.ts](src/lib/red/conexion.svelte.ts) keeps up to date with the host's `Vista`/`Cambios`, emitting `partida-cambiada` so stores re-read (`partida.alCambiarPartida`; it will also serve the host in stage 2). Host-only actions are hidden or disabled with `esJugador` (⚙, create/rename/delete/reorder, the share checkbox, the order of «Fichas activas», `clean`, the ficha's zone/«único»/delete); what a player may do with a ficha is gated by `partida.controla(instancia)` (host: always; player: fichas in their bank), and the host re-checks every request. For players, `urlDeImagen` gives `<base>/__imagen?ruta=…`, answered by the Service Worker from the connection (fallback without SW: the host's `/imagen`), and `obtener_miniatura` returns the path marked with the thumbnail type (`rutaMiniatura`).
- **Transport.** `servidor::atender` serves one player from start to end over a `Transporte` ([transporte.rs](src-tauri/src/red/transporte.rs)): two queues of `Trama` (text = a protocol JSON message, binary = an image chunk). The WebSocket is adapted by `desde_websocket` (pings included); WebRTC (stage 3 of the network plan) will be another adapter. The outgoing queue is bounded: senders wait if the player reads slowly, and a player who cannot take a message in `TIEMPO_ENVIO` (30 s) is cut. Tests can drive `atender` with `transporte::en_memoria()`.
- **Images over the connection (protocol 6).** [red/imagenes.rs](src-tauri/src/red/imagenes.rs): `PedirImagen` → `ImagenCabecera` + binary chunks of 16 KiB (`TROZO`, 1 type byte + u32 id + data, read from disk chunk by chunk), ≤ 4 at a time and 64 queued per player (else `ImagenError("ocupado")`); `SubirImagen` + chunks → `SubidaOk`/`SubidaError` (≤ 2 at a time, ≤ 8 MiB). ONE rule for both ways of asking: `imagenes::localizar` (visibility) and `imagenes::guardar_subida`, also used by the HTTP fallback `/imagen`. In the browser, [imagenesRed.ts](src/lib/red/imagenesRed.ts) (queue of 6, chunk assembly, Cache API cleared on leaving) and [service-worker.ts](src/service-worker.ts), which only answers `<base>/__imagen?…` by asking the page (`postMessage`); it caches nothing of the app. It is registered by hand from `conexion.svelte.ts` (`kit.serviceWorker.register: false`), never in the host; `conexion.lista` waits ≤ 3 s for it to control the page, else the HTTP fallback is used.
- **Shape.** The host runs its own server (axum on 127.0.0.1: `/ws` and the fallback `/imagen`, `servidor.rs`), published by a Cloudflare quick tunnel (`tunel.rs`: `cloudflared` downloaded on first use, pinned `VERSION` + SHA-256 per platform) or by the host's own https address. That choice is per machine, not per game: [red/config.rs](src-tauri/src/red/config.rs), `<app data>/red.json` (separate from `config.json`, which `partidas.rs` rewrites whole), commands `obtener_config_red`/`guardar_config_red` (only with the room closed), UI «Cómo llegan los jugadores» in `VentanaSala`. `Propio { url, puerto }`: the server listens on `127.0.0.1:<puerto>` and the link is `https://<direccion_de_url(url)>/#s=…&k=…`; `Lan { puerto }` («abrir en LAN», Radmin/Hamachi/ZeroTier): listens on `0.0.0.0:<puerto>` and `EstadoSala.enlaces` has one plain `http://<ip>:<puerto>/` per IPv4 (`config::direcciones_lan`, `if-addrs`). **No key in that link** (no `s`/`k`, like a game's LAN): `SalaAbierta::sin_llave()` lets the greeting through without `coincide` only in this mode (the password stays optional; the player caps still apply), and `leerEnlace("", location)` gives `sala = "lan:<host>"` just to remember the player per address. In those two modes the **player page is served by the app itself** ([red/pagina.rs](src-tauri/src/red/pagina.rs), `rust-embed` over `build-jugador/`, built by `bun run web:build:app` with base `/` from `beforeDevCommand`/`beforeBuildCommand`; `build.rs` creates the folder if missing): the link has no `t`, `leerEnlace(hash, location)` takes the page's own host and scheme (`mismoOrigen`, `seguro`), so `ws://` and a relative `/imagen` in LAN. Cloudflare keeps GitHub Pages (its address changes on every opening and the browser would lose the remembered players). Accepted origins and token-proof addresses come only from the open room (`Red::acepta_origen`, `SalaAbierta::direcciones`/`origenes_propios`), never from the `Host` header. In `http://` (LAN) there is no `crypto.subtle` nor Service Worker: `prueba()` uses `@noble/hashes` everywhere, and images use the `/imagen` fallback. The player app is this same SvelteKit app built for the web (`bun run web:build` sets `OPENROLL_WEB=1`: `svelte.config.js` then uses base `/OpenRoll` and writes `build-web/`) and published to GitHub Pages (`.github/workflows/cliente-web.yml`); `bun run web:dev` serves it on port 5173. `URL_CLIENTE` is in `red/mod.rs`, overridable at compile time with `OPENROLL_URL_CLIENTE`. Data flows host ↔ player only, never player ↔ player.
- **Direct connection (WebRTC, «Peer to peer»; protocol 10: 8 added `OfertaDirecta`, 9 the notice colors, 10 `entrar_igualmente`).** The main way: the player talks straight to the host, the tunnel/own address is only the fallback. Host side [red/webrtc.rs](src-tauri/src/red/webrtc.rs) (`webrtc` 0.21.1; why it was chosen: docs/red.md, «Por qué webrtc-rs»): `responder` checks the player's code (`red/codigo.rs`: AES-256-GCM + deflate with a key from the link secret, ≤ 10 min old, nonce used once, ≤ 8 half-open peers) and answers as soon as the first `srflx` candidate (+300 ms) or at 1.5 s, never waiting for «gathering complete». When the three channels the browser opens are up (`juego` reliable, split in ≤ 16 KiB chunks by `red/trozos.rs`; `imagenes` reliable; `arrastre` unordered with no retransmits) it builds a `Transporte` and runs the SAME `servidor::atender`, so greeting, password, permissions and caps are identical. Identity: `sala.json` has a DTLS certificate (`SalaGuardada.certificado_dtls`, renewed with a new link) whose SHA-256 fingerprint goes in the link as `f` (base64url, 43 chars) and the browser refuses an answer with another; the token proof over this path is bound to `webrtc:<fingerprint>`. Only in peer to peer (no certificate/fingerprint in LAN mode). Signalling is AUTOMATIC and goes FIRST through the host's own server (protocol 8: `OfertaDirecta { codigo }` before `Hola` on the fallback WebSocket → `RespuestaDirecta`/`OfertaDirectaError`, handled in `servidor::atender` via `Red::responder_oferta`, which applies the shared 6 offers/min cap; one per connection; `Conexion.#negociar`, 4 s) and, only with Cloudflare (its quick tunnel has no service guarantee) and if that does not answer, through public Nostr relays as plan B. With the own address there are NO relays (the page is served by the host through that address, so if it is down nothing loads and relays would be useless; no `r`, no third party sees the IP). Relay part: ([red/senal.rs](src-tauri/src/red/senal.rs) ↔ [senal.ts](src/lib/red/senal.ts)): the player publishes its offer (the same encrypted code, as the content of an ephemeral kind-27184 event signed with a fresh Schnorr key) and the host, listening since the room opened in peer to peer on the relays it picked, answers with `webrtc::responder_con` and publishes the answer; relay tags are HMACs of the link secret (the answer also carries `x` = the offer's `n`), so relays see only opaque blobs, and the browser still checks the fingerprint. Caps: 6 offers/min, events ≤ 32 KiB, `created_at` ±2 min, an event seen once. Relays are NOT a fixed list: when the room opens the host probes `senal::CANDIDATOS` (`Red::iniciar_senal` → `senal::elegir_de`: one connection subscribes to a fresh tag, another publishes a ~3 KB ephemeral event, both must see it, 6 s cap) and keeps the first 4 that pass in `SalaAbierta.reles`; they travel in the link as `&r=host,host` (`enlace.reles`, domain names only, max 6; a link without `r` uses no relays). If none passes, the link keeps `f` (direct is still negotiated through the tunnel) but has no `r`. Regenerating the link reuses the same relays. To add candidates, edit `CANDIDATOS` (`wss://host`, no path). TLS for the relays uses an explicit `ring` rustls provider (two providers live in the process: the default one would panic). Regenerating the link restarts the listener. The player does nothing: `conexion.svelte.ts` tries direct through the server ONLY (WebSocket opens ≤ 2 s; answer ≤ 2.5 s counted from when the offer is sent; then the channels talk ≤ 6 s); server and relays are never tried at once (no needless IP sharing with third parties). If the server does not negotiate, it enters through the fallback AT ONCE and, if the link has relays, tries them in the background once inside (`#mejoraPorReles`, ≤ 6 s) and switches by itself if the direct link opens (same path as a reconnection; no switch without a stored token); if it negotiated but the channels do not open, it enters through the fallback and remembers the failure. The host sees how each player came in: `Transporte.via` → `Conexion.via` → `JugadorSala.via` (badge «Directo» / «Respaldo» / «Red local» in `VentanaSala`) and `EstadoSala.senal` («relés conectados N de M»). «Túnel» option in the window (= `ConfigRed.solo_respaldo`, `SalaAbierta::directa()`): no `f` in the link, no certificate, no relays, so players never see the host's IP. If a direct connection that had worked drops, the player falls back and retries direct in the background (30 s / 2 min / 5 min, `#mejorarADirecto` with deferred listeners, only with a stored token) and switches through the reconnection path; messages from a stale transport are ignored (`#idTransporte`). A failed direct attempt is remembered 30 min in `localStorage` (`openroll.directo.<sala>`) so the next visit enters by the fallback at once. ICE fails at 30 s and a half-open peer frees its slot at 45 s. Cloudflare links carry `f` too. Player side: [transporte.ts](src/lib/red/transporte.ts) (`TransporteCliente`: WebSocket or direct), [webrtc.ts](src/lib/red/webrtc.ts) (`crearDirecto`, `usarRespuesta` checks the fingerprint), [codigo.ts](src/lib/red/codigo.ts), `trozos.ts`; `conexion.svelte.ts` goes direct first when the link has `f` and the browser can (`soportaDirecto`), and falls back to the WebSocket (`conectarPorRespaldo`) on any failure or when a direct connection drops. There is no manual-code screen any more (the codes are only the relay payload). Live drag: `MensajeCliente::Aviso` (no reply/queue) and `n` in `Arrastre`/`ArrastreFin`; `Trama::Efimero` goes over `arrastre`. Rust/TS share fixed test vectors for the codes.
- **Link** `URL_CLIENTE#t=<tunnel>&s=<sala>&k=<secreto>`: the tunnel changes every time the room opens; `s`/`k` live in `<partida>/sala.json` (`sala.rs`) and change only with «Generar enlace nuevo», which also forgets every remembered browser.
- **`sala.json` is host-only**: never in `EstadoPartida` nor in the delta log. It holds the Argon2id password hash (optional) and, per remembered browser, `SHA-256(token)`. The token travels ONCE (`Bienvenido`); afterwards the browser answers the host's `Reto` with `HMAC-SHA256(SHA-256(token), "<reto>|<túnel>")` (`sala::prueba`, mirrored in `src/lib/red/conexion.svelte.ts`; both sides test the same fixed vector), so a fake link pointing elsewhere cannot steal it.
- **What leaves.** Only `red::vista::vista_para` (built on `visibilidad.rs`): the shared maps and their zones, the player's own fichas whole, the other instances of those maps filtered, and only the parameter definitions they can see. After every delta, `partida::registrar` calls `red::tras_cambio`, which sends each connected player the `diferencias` from what they last got. Images are given only if `recurso_visible_para` allows them (or the player uploaded them); for the HTTP fallback the image session is one per player and survives reconnections (dropped when expelled, on a new link and when the room closes).
- **Rules.** Lock order: the game state first, then `Red::dentro` (server tasks never take the state while holding it). `AppState.estado`/`almacen` are `Arc` so the server can register deltas (`JugadorRegistrado` when someone joins; `asignar_propietario` gives a ficha with `EntidadCambiada { Propietarios }`, also by dragging a player from the room window onto a ficha, [arrastreJugador.svelte.ts](src/lib/arrastreJugador.svelte.ts), targets marked `data-id-entidad` plus a board resolver). While the room is open (or opening) the game cannot be switched (`cambiar_de_partida` refuses; «Partidas…» is disabled). Closing the window closes the room (`cerrar_partida`). Both the «Cerrar sala» button (`cerrar_sala`) and closing the window use `Red::cerrar_avisando`: it sends `SalaCerrada` to every connection and WAITS (≤ 1.5 s + a short grace) for those connections to finish writing it BEFORE stopping the server and killing the tunnel (a plain `cerrar()` queued the notice and the tunnel/process died right after, so players saw a drop and «Reconectando…» instead of «El host ha cerrado la sala»). The player ends in the same «Fuera de la sala» screen as when expelled (`#terminar`, no reconnect attempts). Changing a message in `protocolo.rs` means changing `src/lib/red/protocolo.ts` and bumping `VERSION_PROTOCOLO` on both sides (and publishing the web build together with the app).

- **Player actions.** `invoke` of a write command in `PETICIONES` ([replica.ts](src/lib/red/replica.ts)) becomes `Pedir { id, peticion: { cmd, ...args } }` over the WebSocket (`Conexion.pedir`, 30 s timeout); the host answers `Respuesta` AFTER the `Cambios` it caused (same channel), so the replica is up to date when the player's screen re-reads. On the host, [peticiones.rs](src-tauri/src/red/peticiones.rs) decodes it against the whitelist (`Peticion`), checks it with the pure `permitida` (owner only; only shared maps as destination for players, the host has no such limit; `cambio_permitido`; photo only if the player uploaded it; `.txt` only in the ficha's folder) and runs it with the SAME function as the Tauri command: **every whitelisted command is split into `xxx_en(…, &AppState)` (the logic) and the `#[tauri::command]` wrapper that only calls it** (`partida.rs`), so one rule serves both and tests need no Tauri. Adding an action = `Peticion` variant + `permitida` case + `ejecutar_en` case + `PETICIONES` name + tests. Requests of one connection run in order, max 30/s. After a request the host emits `partida-cambiada` (`tiradas` or `entidades`) so its screen re-reads, and a player's ping/path reaches the host (`aviso-tablero`) and the other players; a player's focus is local (never sent).
- **Shared chat.** `tirar_dado_de(estado, jugador, comando)` (dados.rs) runs in the host's Rust and stores `Tiradas { jugador, autor }` (name of the roller, empty for the host); the whole chat travels in `VistaJugador.historial_tiradas`/`Cambios`, so everyone sees everyone's rolls as «Ana: 1d20 (7) = 7» (`tiradas.cargar()` re-reads after a roll instead of adding the line locally). Only the host can `clean`, and only the host can roll in private (`Tiradas.publica = false`, checkbox «Pública» in `BarraDados`): `vista_para` drops those from players' chat. The player loads the chat on entering (`tiradas.cargar()` after `partida.iniciar()`). Each player's ↑ ↓ history is saved on the host's disk (`historial_jugador_<id>.txt` via `Almacen::anadir_historial_de`), fetched on connect with the `obtener_historial_personal` request, and deleted by `eliminar_jugador`.
- **The player follows the host's map.** The player does NOT choose the map: `partida.seleccionarMapa` does nothing for them, and `mapaActual` comes from the replica command `obtener_mapa_visible`. The host tells Rust which map it opened with `abrir_mapa` (called from `partida.#abrirMapa`; ephemeral, kept in the `#[serde(skip)]` field `EstadoPartida.mapa_del_host`, never in the log). `visibilidad::mapa_visible` gives the open one if it is shared, else the last shared one the host opened (so entering a private map, or going back, changes nothing for players), and travels as `VistaJugador.mapa_visible` / `Cambios.mapa_visible_cambiado` (protocol 5). The map list still shows every shared map (thumbnails); a player's list jumps to the zone of the new map only when the host's map really changes.
- **Update notice for the host (when the app starts).** `sala.iniciar()` (called by `+page.svelte` on mount) runs `comprobar_version_web` (`red/version.rs`) once at startup, whatever the room mode: it fetches `URL_CLIENTE + version.json` (6 s, ≤ 4 KiB, a single request, only to our own page; the web build publishes `{ protocolo, app: <Cargo.toml version> }`, prerendered in `src/routes/version.json/+server.ts`) and `evaluar(.., jugadores_usan_la_web)` gives a «suave» notice if the web's app version is newer than the app's, and a «fuerte» one (players cannot enter until the host updates) only when `red.json` says Cloudflare (`jugadores_usan_la_web`, the players' page is GitHub Pages, which updates on every push while the installed app does not) and the web protocol is newer. No network / invalid file = no notice. It shows as a 6 s toast with the clickable link `URL_DESCARGAS` (the repo's releases page, `notificaciones.mostrar(.., { largo, aviso, enlace })`, opened with `@tauri-apps/plugin-opener`) and stays as a line in the room window (`sala.avisoVersion`). To test without touching the repo: serve a fake `version.json` from a temp folder and build with `OPENROLL_URL_CLIENTE=http://localhost:8000/`. The player's version-mismatch rejection says «Tu navegador y el host usan versiones distintas de OpenRoll. Recarga la página; si sigue igual, pídele al host que actualice la app».
- **Same name from another device (protocol 10).** A device without a token that types the name of an already registered player is NOT blocked when nobody uses it: `identificar` (`servidor.rs`) answers `Identificate { nombre_existente }` and the player sees «Ya existe un jugador con ese nombre registrado. Entrar igualmente (no se perderán los permisos de las fichas)» (`EntradaSala.svelte`); `Unirse { entrar_igualmente: true }` enters as THE SAME player (same id, fichas and permissions, no new player) with a new token of its own (`nuevo_token`, max 8 per player). It is blocked as before (plain error, nothing offered) while that player is `Red::esta_presente` (connected, or its connection closed < `VENTANA_RECONEXION_MS` ago). The room password is checked BEFORE anything is offered. `jugadores::existente` finds the player (case, spaces and invisible chars as in `registrar`). Accepted risk: anyone with the link (and password) can claim an offline player by typing the name; the host gets the «se unió» notice and can expel (that revokes all its tokens).
- **«x se unió a la sala» (host only).** `Red::conectar` returns `(id_conexion, nueva)`: a connection is NOT new if it replaces an open one of the same player or if that player's previous connection closed less than `VENTANA_RECONEXION_MS` (60 s, what the browser keeps retrying) ago (`SalaAbierta.cerradas`, noted by `desconectar`, never by expel / new link). `atender` emits the Tauri event `jugador-unido { id, nombre }` to the host's screen only for new ones; `+page.svelte` shows it through the screen-only store [notificaciones.svelte.ts](src/lib/notificaciones.svelte.ts) (a stack over the top-left of the board, `Notificaciones.svelte`, each toast with its OWN 3 s timer, max 8).
- **Removing a player.** `eliminar_jugador` (comandos.rs, `eliminar_jugador_en`): expels them (token forgotten, drafts cancelled) and registers `DeltaPartida::JugadorEliminado`, which drops them from `jugadores` and from every `propietarios` (bank, instances, bin). It never blocks because of their fichas: they become host-only. UI: «Quitar de la partida» in `VentanaSala`.
- **Own fichas.** A player creates a ficha like the host (draft with a reserved id → save / cancel) through the host: `iniciar_borrador_entidad`, `crear_entidad`, `cancelar_borrador_entidad` are whitelisted (`permitida_con` also gets the player's drafts, tracked in `Red::borradores`). The host picks the zone (the requested one if the player sees it, else the first with a shared map) and on save FORCES `propietarios = [player]` and `es_unico = false`. Caps: `MAX_BORRADORES_POR_JUGADOR` (3) open drafts and `MAX_FICHAS_PROPIAS` (20) fichas. `.txt` attachments of a draft count as the player's. When the player leaves (room closed, expelled, new link) their drafts are cancelled through `Red::poner_limpiador` (set in `lib.rs`), so no reserved id is left behind.
- **Old backgrounds.** Very old versions stored a map background (or ficha photo) as a URL of a file on the host's disk (`http(s)://asset.localhost/<encoded path>`). `migrar_fondos_antiguos` (partida.rs, run before `corregir_tamanos_mapas` at startup and in `cambiar_de_partida`) copies them into `imagenes/` with a normal delta each (`MapaModificado` / `EntidadCambiada { Foto }`), so they can be measured, protected by `recursos` and served to players; a missing file is left as is.
- **Photos.** A player uploads a ficha photo over the connection (`SubirImagen`, see above; ≤ 8 MiB, raster formats only, content checked in `imagenes::importar_bytes`, ≤ 20 per session; no ficha needed, so a player can drop an image on the bank to create their own); the path is noted as theirs (`Red::subidas`) so only they can see it and use it until a ficha does. There is no `POST /subir` any more. The fallback `/imagen` sends CORS for the page origin, and EVERY response carries `Vary: Origin` so the browser never reuses for the thumbnail `fetch` (`cargarImagen`, `cache: "reload"`) the copy an `<img>` left without CORS. A failed thumbnail save shows a line (`partida.avisar`) instead of staying silent.

### Dice
The parser and roller live in Rust ([dados.rs](src-tauri/src/tablero_general/dados.rs), command `tirar_dado`, limit of 999 dice in total). The result breakdown is HTML with `<b>` marking a 1 or the max face. The frontend ([src/lib/tiradas.svelte.ts](src/lib/tiradas.svelte.ts)) only builds command strings (`aplicarDadoAlComando` is a pure, tested function) and keeps the history and arrow-key navigation. `clean` or `c` ON ITS OWN (`es_comando_limpiar`, mirrored by `esComandoLimpiar`) clears the chat through the command `limpiar_chat` and the delta `HistorialTiradasLimpiado`; mixed with anything else it goes to `tirar_dado` and is an invalid roll.

### Frontend state
Global singleton stores in `src/lib/*.svelte.ts` (Svelte 5 runes, class with `$state`/`$derived`): `partida` and `tiradas`. Components import them and read or call methods directly. Don't add prop or callback chains for shared state. Grid (`rejilla`) edits are debounced 5 s before being saved. Screen-only preferences that are not part of the game (e.g. hiding the grid edit bar, toggled from ⚙) live in [ajustesVista.svelte.ts](src/lib/ajustesVista.svelte.ts), saved in `localStorage`, never in Rust. Help tooltips (the tutorial-style `title` texts) go through `ayuda(texto)` from the same file, so «Quitar tutoriales» (⚙, `ajustesVista.tutoriales`, chosen separately by host and each player, who also get the ⚙ button with only that option) hides them all: wrap every new help `title` in `ayuda(...)`. Components live under `src/routes/componentes/` (left panel = zones/maps/entity bank, right panel = active tokens/dice chat, `Tablero` = board canvas, `VentanaFicha` = non-modal entity editor). Opening a ficha (bank row, «+ Añadir Ficha», an image dropped on the bank) while another is open SAVES the open one first (`partida.abrirEditorEntidad` calls the save that `VentanaFicha` registered with `partida.registrarEditor`) and then shows the new one; if the save fails, the open one stays with its error. `+page.svelte` keys the window on `partida.sesionEditor`, so each ficha gets a fresh `EditorFicha`, and the window keeps its last position. `VentanaFicha` is view-only: its logic (files created during the edit session, attached `.txt` contents, validation, save/cancel/delete) lives in the `EditorFicha` class in [src/lib/editorFicha.svelte.ts](src/lib/editorFicha.svelte.ts), and its subcomponents are in `componentes/ventana-ficha/`. Drag & drop from the OS goes through `alSoltarArchivos` in [src/lib/soltarArchivos.ts](src/lib/soltarArchivos.ts). Tauri reports drops for the whole window, so each component checks which element is under the cursor.

### Tests
- Frontend tests in `tests/` run in Node. They replace `@tauri-apps/api/core` with an in-memory fake backend via `vi.resetModules()` + `vi.doMock(...)`, then import the store fresh. Follow that pattern, and extend the fake's `switch (cmd)` when the store calls a new command.
- Rust tests are inline `#[cfg(test)]` modules. Use `almacen::pruebas::dir_temporal(name)` for an isolated data dir.

### Dev-only behavior
In debug builds, `Almacen::migrar_desde(cwd)` copies old `partida.json`/`deltas.jsonl` from the working directory (`src-tauri/`) if the data dir is empty. Only when a brand-new «Partida 1» was just created. Those filenames are gitignored.
